3. BEHAVIOUR HIGHLIGHTS
======================================================================
Key hierarchy
  - MVK is a random 256-bit key (not derived from the pattern).
  - Pattern envelope: PBKDF2-HMAC-SHA256 (16-byte random salt, 600,000 iterations by default,
    configurable for tests) -> AES-256-GCM wrap with a fresh 12-byte IV.
  - Recovery envelope: independent salt/IV/KEK from a 9-word BIP-39 phrase (99 bits).
  - Envelopes are role-bound via AAD, so a pattern cannot open the recovery envelope and
    vice-versa.
  - Blobs are bound to namespace id + item id via AAD; the index to the namespace id.

Plausible deniability
  - namespace = hex(PBKDF2-HMAC-SHA256("vaulty-ns:v2:" + normalizedPattern,
    salt "vaulty-ns-salt:v2", kdfIterations)); default 600,000 iterations, same as the envelopes.
  - unlock() opens an existing vault or silently creates an empty one. There is no
    "wrong pattern" error. New vaults return the recovery phrase once; it is never stored.

Duress
  - Runtime option duressPattern, or a duress flag stored only inside an ENCRYPTED index of a
    decoy-looking vault (no plaintext marker anywhere).
  - Wipe order: zero the MVK and drop the index synchronously; then purge adapter namespaces,
    OPFS, all IndexedDB databases, Cache API, localStorage, sessionStorage (fail-open per step);
    then return { status: 'duress_triggered' }.

Archives (.vault)
  - Layout: "VLT1" + version + flags + namespace id + both envelopes + encrypted index +
    encrypted blobs + trailing SHA-256 checksum.
  - Import accepts the pattern or the 9-word phrase, optional newPattern to re-key. Every blob is
    authenticated BEFORE anything is written to storage; keys.bin is written last.

Extras not in the brief: removeDuress(), the newPattern import option, the static security
checker with its own tests, readArchiveHeader().

5. KNOWN LIMITATIONS AND RISKS (full detail in .kiro/specs/vaulty-core/design.md section 7)
======================================================================
T3  HARDENED (see addendum below). The namespace id was originally a fast SHA-256 of the pattern;
    it is now domain-separated PBKDF2-HMAC-SHA256 at the configured kdfIterations. Residual: the
    namespace salt is a public constant, so precomputation across installs is possible, and
    kdfIterations is now part of the vault address.
T1  Patterns are low entropy. 6 ordered distinct nodes is about 1.3e8 possibilities (~2^27).
    The 99-bit recovery phrase is the strong secret.
T8  Per the spec, an undecryptable namespace is silently replaced by an empty vault, so
    corruption leads to data loss. Regular .vault exports are the mitigation.
T4  The number of namespace containers on disk is observable (including decoys and duress
    vaults). No global metadata file exists.
T5  A runtime-option duress match returns faster than a normal unlock (no key derivation);
    the in-vault duress path does not have that timing difference.
T6  JS strings, GC copies and CryptoKey internals cannot be zeroed. Only the raw MVK bytes are.
T9  XSS, malicious extensions, compromised OS and keyloggers are out of scope.

Other notes
  - Coverage is below 100% and there is no mutation testing yet.
  - The save-hook JSON is valid and the file pattern is correct, but I have not confirmed that
    Kiro triggers it on save.
  - Tests use kdfIterations: 1000 for speed; one test asserts the 600,000 default.

ADDENDUM - T3 HARDENING (namespace id)
======================================================================
Change
  deriveNamespaceId(pattern, { kdfIterations }) is now
    hex( PBKDF2-HMAC-SHA256( "vaulty-ns:v2:" + pattern, salt "vaulty-ns-salt:v2", kdfIterations, 32 bytes ) )
  with kdfIterations defaulting to 600,000, i.e. the same cost as the key envelopes. Folder names
  on disk (and the namespaceId in a .vault header) can no longer be confirmed faster than
  attacking keys.bin. The prefix and salt differ from the KEK derivation, so the id is an
  independent PBKDF2 output.

Files touched
  src/crypto.ts, src/vault.ts, src/index.ts, tests/crypto.test.ts, tests/vault.test.ts
  .kiro/specs/vaulty-core/design.md (section 3.1 new, diagram, flows, T2/T3/T4, testing)
  .kiro/specs/vaulty-core/requirements.md (glossary, R2.5, new R2.7/R2.8, R7.1)
  .kiro/specs/vaulty-core/tasks.md, REPORT.txt

Verification (exact commands run: `npm test && npm run build` at the repo root; exit 0)
  Tests:       205 passed (6 files); was 195, +10 new namespace tests
  Typecheck:   0 errors;  check:security: clean
  Build:       ESM + CJS + d.ts success
  Bundle check: with production defaults, the folder created by the built ESM and CJS bundles equals
                an independent Node pbkdf2Sync computation at 600,000 iterations.
  Coverage was not re-measured after this change.

Behaviour changes to know about
  - kdfIterations is now part of a vault's address: a client with a different setting will not
    find existing vaults (it silently creates a new empty one).
  - One extra PBKDF2 per unlock (open: 2, create: 3), per configureDuress/removeDuress, and per
    importArchive with newPattern. A runtime duress match still performs no KDF.
  - Vaults created by earlier development builds (SHA-256 folder names) are not found; restore
    them from a .vault archive with importArchive(..., { newPattern }). No migration was written
    because 0.1.0 is unreleased.
  - Archive format is unchanged (version 1).

Residual risk
  - The namespace salt is a public constant, so an attacker can precompute folder names for the
    most likely patterns once and reuse the table against every install. A per-install salt would
    close this but needs a non-secret global file and breaks cross-device addressing.
  - Pattern entropy itself is unchanged (T1).
